# 第 1 章 选题定位

## 1.1 问题提出：原创性证明的信任缺口

学术成果的原创性认定，长期依赖"平台出具结论 + 使用方采信"的模式。这套模式在三个环节上存在结构性缺口。

### 1.1.1 缺口一：查重结论不可独立验证

现有查重（文字复制比）系统的工作方式是：用户上传全文 → 平台内部比对其私有比对库 → 返回一个**百分比**。

问题在于，这个百分比是**平台的自证结论**：

- 比对库是平台私有的，第三方无法复现同样的计算；
- 报告的生成过程不可审计，**报告本身可以被修改甚至伪造**（一张 PDF 截图无法自证真伪）；
- 换一家查重平台，同一篇稿子可能给出差异明显的数值。

结果是：期刊、竞赛组委会、教务部门即便拿到报告，**在技术上也无法独立确认这份报告对应的是否是当前这份稿件**。

### 1.1.2 缺口二：AIGC 贡献无据可查（本作品的核心切入点）

大模型进入写作流程后，出现了新的、且**现有机制完全没有覆盖**的问题：

> **一篇稿子里，哪些是作者写的、哪些是 AI 生成或改写的，目前没有任何可验证的记录手段。**

当前的现实处理方式有三种，都不成立：

| 现实做法 | 为什么不成立 |
| --- | --- |
| 让作者自觉申报 | 申报表是单方可改的，且**事后可以否认或改口**，无约束力 |
| 用 AI 检测器判断 | 检测器本身是概率模型，存在误判，且**不能区分"AI 生成"与"AI 润色"**；检测结果同样由平台自证 |
| 一刀切禁止 | 现实中无法执行；且把"用 AI 润色"与"让 AI 代写"等同处理，对诚实使用者不公平 |

**这正是本作品的切入点。** 本作品不试图去"检测"AI，因为检测在原理上就不可靠；而是让作者**主动、不可篡改地声明** AI 的参与程度，并把这个声明与成果内容**在同一时刻、同一不可篡改的载体上**固定下来。

一旦上链，作者**事后无法改口**——这才是评审方真正需要的可信依据。作者越诚实，声明越有价值；想造假的人，将无法在事后抹掉自己留下的声明。

### 1.1.3 缺口三：时间戳争议

代码作业、竞赛作品、课程设计普遍存在"谁先谁后"的认定需求。

- 文件系统的创建/修改时间**可被轻易修改**，无证据效力；
- 邮件、聊天记录、网盘上传时间**由各自的中心化服务商掌握**，可被单方调整或删除；
- 一旦发生纠纷（如两人提交高度相似的代码），**双方都拿不出让对方信服的时间证据**。

### 1.1.4 缺口四：成果确权脆弱

原创性存证若依赖单一机构的数据库：

- 数据库被篡改、误删、或机构停止运营，**存证记录随之失效**；
- 记录方即验证方，**"自证"在逻辑上不构成证明**。

### 1.1.5 四个缺口的共同本质

上述四点看似分散，本质是同一个问题：

> **原创性的"证明"与"验证"被集中在同一个主体手中。**

记录结论的人同时是判定结论的人，第三方只能选择信任。**本作品的定位，就是把这个被合并的两个角色重新拆开。**

## 1.2 为什么必须用区块链（本作品的技术必要性论证）

**这是本作品必须回答的核心问题。** 如果一个功能用普通数据库就能做好，那它就不应该用区块链。逐条论证如下：

| 需求特征 | 中心化数据库 | 区块链 | 本作品是否需要 |
| --- | --- | --- | --- |
| **多方互不信任** | 记录方 = 验证方，自证无效 | 任何一方可独立读取链上数据 | ✅ **强需要** |
| **结论须可被第三方独立复现** | 依赖平台开放接口与其诚信 | 拿原文重算哈希即可自行验证，**无需访问本平台** | ✅ **强需要** |
| **记录一经写入不可事后修改** | 管理员权限即可改库 | 写入即固化，**本平台自己都改不了** | ✅ **强需要** |
| 高并发写入 / 大数据量存储 | 擅长 | 不擅长 | ❌ 不需要（原文不上链） |
| 复杂查询 / 全文检索 | 擅长 | 不擅长 | ❌ 不需要（链下完成） |

**结论**：本作品的需求恰好落在区块链的强项区（**多方互不信任 + 独立可验证 + 不可篡改**），
而它的弱项区（大数据量、高并发、复杂查询）**通过架构设计被完全规避**——因为只有 32 字节的哈希指纹与少量关键状态上链，原文与计算全部留在链下（见第 2 章）。

### 1.2.1 关键设计：让"验证"不依赖本平台

本作品采用 **内容哈希 + 链上时间戳** 作为唯一的证明凭据：

1. 作者在**浏览器本地**对文件计算 SHA-256 指纹（32 字节）；
2. 指纹与元信息写入区块链，获得链上时间戳；
3. 任何第三方拿到该文件后，**用任何工具**重算 SHA-256，再到链上查询该指纹是否存在。

整个验证过程中，**第三方不需要访问本平台的服务器，也不需要信任本平台**。
本平台即使全部下线，只要区块链还在，存证记录与验证能力就依然存在。

> **这是本作品与"区块链存证"类产品的关键区别所在**，也是第 1.3 节竞品对比的主线。

## 1.3 竞品与现有方案对比

| 方案 | 记录介质 | 第三方可否独立复现 | 可否事后篡改 | 是否覆盖 AIGC 贡献 | 主要局限 |
| --- | --- | --- | --- | --- | --- |
| 知网 / 万方查重 | 平台私有库 | ❌ 不可（算法与库不公开） | 报告可 PS | ❌ 无 | 结论自证；报告无法与具体稿件绑定 |
| Turnitin | 平台私有库 | ❌ 不可 | 报告可 PS | ⚠️ 有 AI 检测但为概率判断 | 同上；AI 检测存在误判且不可解释 |
| 通用 AI 检测器 | 模型输出 | ❌ 不可 | 结果可截图伪造 | ⚠️ 仅给概率分 | 原理上不可靠；无法区分生成与润色 |
| 传统时间戳服务（TSA） | 中心化授时机构 | ⚠️ 部分可（依赖机构存续） | 机构侧可改 | ❌ 无 | 记录方即验证方；机构停运即失效 |
| 网盘 / Git 版本历史 | 服务商数据库 | ❌ 不可 | 服务商可改 | ❌ 无 | 时间由服务商掌握，无独立证据效力 |
| 通用区块链存证平台 | 链上 | ✅ 可 | ❌ 不可 | ❌ **普遍缺失** | 面向合同/版权，**未解决学术场景的 AIGC 申报问题** |
| **科研链证（本作品）** | **链上指纹 + 链上 AIGC 声明** | ✅ **可（浏览器本地重算哈希）** | ❌ **不可** | ✅ **有（核心功能）** | 见第 4 章完成度说明 |

**差异化定位一句话**：

> 现有产品要么"结论由平台自证"（查重类），要么"没有 AIGC 维度"（通用存证类）。
> 科研链证补的是中间那块空白——**把 AIGC 贡献声明变成一条不可篡改、可被任何第三方核验的链上记录**。

## 1.4 目标用户与应用场景

### 1.4.1 三类角色

| 角色 | 诉求 | 在本作品中的能力 |
| --- | --- | --- |
| **作者**（学生 / 研究者） | 证明"这是我在何时完成的"，并如实申报 AI 使用情况 | 登记成果、声明 AIGC、追加版本 |
| **核验方**（期刊 / 竞赛组委会 / 教务） | 独立确认手里这份文件与作者申报是否一致 | **拖入文件即得结论，无需登录、无需钱包** |
| **仲裁方**（教务 / 组委会） | 处理争议、查看完整履历 | 查看时间轴与版本历史、发起争议登记 |

### 1.4.2 四个典型场景

| 场景 | 痛点 | 本作品给出的能力 |
| --- | --- | --- |
| 课程论文 / 毕业设计提交 | 教师无法核实"是否为本人所写、AI 用了多少" | 学生提交时一并给出存证编号，教师拖入同一文件即可核验 |
| 学科竞赛作品提交 | 作品完成时间与原创性易起争议 | 链上时间戳 + 版本追加，形成完整过程留痕 |
| 代码作业查重纠纷 | "谁先谁后"无时间证据 | 两份代码各自的链上登记时间可独立比较 |
| 期刊投稿的 AI 使用申报 | 现有申报表可事后否认 | AIGC 声明上链，**一经写入不可改口** |

### 1.4.3 明确不做（防止范围蔓延，也便于评审理解边界）

本作品**不替代**任何写作或投稿平台，**不做**：

- 真正的查重算法 / NLP 相似度模型（这是另一个研究课题）
- PDF 内容解析与语义比对
- 用户注册 / 登录 / 找回密码系统（**钱包地址即身份**）
- 移动端 App / 小程序
- 对接知网、arXiv、期刊投稿系统（无公开 API、无授权、亦无必要）

**边界清晰是本作品的设计选择**：只做"存证与核验"这一层，因此没有做不完的集成工作，也更容易做扎实。

## 1.5 价值主张与前景

### 1.5.1 一句话价值主张

> 科研链证**不替代**任何写作或投稿平台。它是一个**独立第三方存证与核验服务**——
> 作者在任何地方写完论文/代码，都能在这里留下一个不可篡改的「指纹」；
> 任何评审方、期刊、竞赛组委会都能**独立验证**其原创性与 AI 使用情况，
> **而不需要信任存证平台本身**。

### 1.5.2 三层价值

| 层次 | 价值 |
| --- | --- |
| **对作者** | 低成本获得一份"完成时间 + 内容一致性 + AI 使用情况"的可信凭证，保护自己的在先权利 |
| **对核验方** | 从"采信平台结论"变为"自行复现结论"，**把信任成本降为零** |
| **对学术生态** | 为 AIGC 时代的学术诚信提供一种**可执行、可验证**的机制；鼓励诚实申报而非一刀切禁止 |

### 1.5.3 技术亮点（答辩时须口头强调）

> **文件永远不上传服务器。**

浏览器使用 Web Crypto API 在本地计算 SHA-256，只有 32 字节的指纹上链。原文不经过任何网络请求。

这一设计**同时解决"隐私"与"信任"两个问题**：存证平台自己都拿不到原文，自然无法作恶、也无法被要求交出原文。
它把"信任平台"转化成了"**校验数学**"——这是本作品在工程上最值得强调的一点。

### 1.5.4 推广路径（**规划中**）

| 阶段 | 形态 | 说明 |
| --- | --- | --- |
| 当前 | Sepolia 测试网 + 纯前端 SPA | 【已实现】线上可点即用 |
| 近期 | 部署至云平台，向班级/社团开放试用 | 【规划中】PPT 点名的"部署云应用"加分项 |
| 中期 | 高校联盟链（学校、期刊、竞赛组委会为共识节点） | 【规划中】对应大赛 PPT 的"联盟链环境配置"方向 |

> 中期形态之所以选联盟链：参与方（学校、期刊、组委会）数量有限、彼此需要共享存证但互不完全信任，
> 且不希望存证数据完全公开——这正是**联盟链**的典型适用场景。

# 第 2 章 概要设计

## 2.1 需求分析

### 2.1.1 功能需求

| 编号 | 功能 | 说明 | 优先级 | 状态 |
| --- | --- | --- | --- | --- |
| F1 | 钱包连接与身份绑定 | 连接 MetaMask 获得地址，地址即身份，无需注册 | 必须 | 【已实现】 |
| F2 | 成果登记存证 | 选文件 → **本地算 SHA-256** → 填元信息 → 上链 → 返回成果编号与链上时间戳 | 必须 | 【已实现】 |
| F3 | AIGC 贡献声明 | 声明 AI 工具、介入比例（0-100）、用途 | 必须 | 【已实现，见 4.2 局限说明】 |
| F4 | 成果核验 | 拖入文件 → 本地算哈希 → 查链 → 返回"存在/不存在 + 作者 + 时间 + AIGC 比例" | 必须 | 【已实现】 |
| F5 | 存证详情与时间轴 | 展示完整履历：登记 → AIGC 声明 → 版本追加 → 争议 | 必须 | 【已实现】 |
| F6 | 版本追加 | 同一成果追加新版本指纹，保留历史版本 | 加分 | 【已实现】 |
| F7 | 存证证书导出 | 生成含核验方法的 PDF 证书 | 加分 | 【已实现】 |
| F8 | 争议登记 | 第三方可对成果发起争议 | 加分 | 【已实现】 |
| F9 | 数据看板 | 存证总数、AIGC 比例分布、类型分布 | 加分 | 【已实现】 |

### 2.1.2 非功能需求

| 类别 | 要求 | 设计回应 |
| --- | --- | --- |
| **隐私** | 原文不得离开用户设备 | 浏览器本地计算哈希，**原文零上传** |
| **可验证性** | 第三方可不依赖本平台复现结论 | 哈希算法公开标准（SHA-256），链上数据公开可查 |
| **不可篡改** | 存证记录写入后任何人不得修改 | 智能合约不设修改/删除接口，`admin` 为 `immutable` |
| **低成本** | 核验方零成本、无需钱包 | 核验走只读 RPC 调用（`view` 函数），**gas 消耗为 0** |
| **性能** | 不随存证总量劣化 | 指纹→成果编号为 mapping 直查，**O(1) 核验**；原文与计算在链下 |
| **易用性** | 核验方无需学习成本 | 拖入文件即出结论，**无需登录、无需安装钱包** |

### 2.1.3 需求与设计原则的对应

| 设计原则 | 落地方式 |
| --- | --- |
| 只做"存证 + 核验"一层 | 不做查重算法、不做投稿系统、不做用户系统 |
| 信任最小化 | 平台不持有原文、不可改记录、无管理员特权 |
| 验证平民化 | 核验方只需浏览器 + 文件，不需要钱包也不需要注册 |
| 范围可控 | 见 1.4.3「明确不做」清单 |

## 2.2 系统架构（四层）

```
┌─────────────────────────────────────────────────────────────────┐
│  ① 应用·服务层                                                    │
│  成果登记存证 │ AIGC 贡献声明 │ 成果核验 │ 版本追加 │ 争议登记      │
│  存证证书导出 │ 数据看板                                          │
├─────────────────────────────────────────────────────────────────┤
│  ② 用户层                                                        │
│  作者（学生/研究者）  │  核验方（期刊/竞赛组委会/教务）  │  仲裁方   │
│  —— 钱包地址即身份，无需注册；核验方无需钱包                        │
├─────────────────────────────────────────────────────────────────┤
│  ③ 网络·共识层                                                    │
│  当前：Sepolia 测试网（线上可点 Demo）  【已实现】                  │
│  规划：高校联盟链（学校/期刊/组委会为共识节点）  【规划中】          │
├─────────────────────────────────────────────────────────────────┤
│  ④ 系统架构层（链下）                                              │
│  浏览器本地 SHA-256 计算  │  ethers.js v6 链交互  │  Vue3 SPA     │
│  原文永不上传（仅 32 字节指纹上链）                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2.1 分层依据（**本设计的核心决策**）

| 数据 | 存放位置 | 理由 |
| --- | --- | --- |
| 文件指纹 SHA-256（32 字节） | **链上** | 核验的唯一依据，必须不可篡改 |
| 登记人地址、时间戳、AIGC 比例、成果类型、标题 | **链上** | 需要不可篡改与公开可查 |
| **原文文件** | **用户本地，永不上传** | 隐私保护；同时消除平台作恶的可能性 |
| 大体积元信息 | 链下 / 未来可接 IPFS【规划中】 | 上链成本与必要性权衡 |

> **一句话概括分层原则**：**只有"指纹与关键状态"上链，"原文与计算"全部留在链下。**
> 这既保留了区块链的不可篡改与多方互信特性，又完全规避了区块链在大数据量、高并发上的短板。

## 2.3 核心业务流程

### 2.3.1 流程一：成果登记存证（作者）

```
作者连接钱包
   ↓
选择文件（拖拽 / 点击上传）
   ↓
★ 浏览器本地计算 SHA-256 指纹（Web Crypto API，文件不经过网络）
   ↓
填写元信息：标题、成果类型、扩展元信息（选填）
   ↓
填写 AIGC 声明：AI 工具、用途说明、介入比例（0-100%）
   ↓
调用合约 registerWork(指纹, 标题, 类型, AIGC比例, 元信息)
   ↓
MetaMask 确认交易 → 等待链上确认
   ↓
返回：成果编号（workId）+ 链上时间戳 + 交易哈希
```

**关键设计**：登记前会先查询该指纹是否已存在，避免用户白跑一笔必定失败且消耗 gas 的交易。

### 2.3.2 流程二：成果核验（核验方）—— 本作品的核心场景

```
核验方打开网页（无需登录、无需连接钱包）
   ↓
拖入待核验文件
   ↓
浏览器本地计算 SHA-256 指纹
   ↓
以只读方式查询链上：verifyWork(指纹)
   ↓
┌──────────────┴──────────────┐
│                             │
指纹存在                    指纹不存在
│                             │
展示：                      展示：
✅ 核验通过                 ❌ 核验失败
· 成果标题                   · 本次核验所用指纹
· 登记作者（钱包地址）        · 失败原因说明
· 链上登记时间               · 引导前往登记
· AIGC 介入比例
· 当前版本 / 历史版本
└─────────────────────────────┘
```

**演示的关键一幕**：把已存证文件**改一个标点**后另存，再次核验 → **结论立即由"通过"变为"失败"**。
因为 SHA-256 的雪崩效应，内容上的任何微小改动都会导致指纹完全不同。

### 2.3.3 流程三：版本追加（过程留痕）

```
作者打开存证详情页（仅本人可操作，合约层强制校验）
   ↓
选择新版本文件 → 本地计算新指纹
   ↓
调用 addVersion(成果编号, 新指纹, 新AIGC比例)
   ↓
合约保留历史版本指纹（versionHash[workId][version]）
   ↓
结果：历史版本与当前版本**均可单独核验**
```

### 2.3.4 流程四：争议登记

```
任一第三方（连接钱包）
   ↓
对某成果调用 raiseDispute(成果编号, 争议原因)
   ↓
合约将该成果标记为"争议中"并记录事件
   ↓
存证详情页显示争议状态，时间轴新增争议节点
```

> **设计取舍（如实说明）**：当前争议机制**只做登记，不做裁决**——任何地址都可发起争议，且不可撤销。
> 生产环境需引入质押（发起争议需抵押）与多方仲裁流程。demo 阶段有意从简，见第 4 章。

## 2.4 技术选型

| 层 | 选型 | 选择理由 |
| --- | --- | --- |
| 智能合约 | **Solidity ^0.8.24** | 生态成熟；0.8+ 内置整数溢出检查；使用 **custom errors** 而非 `require` 字符串以节省 gas |
| 合约开发 / 测试 | **Hardhat 2** + Mocha/Chai + `hardhat-gas-reporter` + `solidity-coverage` | 与 ethers v6 集成最好；可直接产出 gas 消耗表与覆盖率报告作为测试数据 |
| 前端框架 | **Vue 3**（组合式 API）+ **Vite** | 上手成本低、构建快；路由级懒加载 |
| 链交互 | **ethers.js v6** | 全项目统一 v6（v6 与 v5 API 差异极大，混用是常见陷阱） |
| UI 组件 | **Element Plus** | 不自己写样式，降低前端调试超时风险 |
| 证书导出 | **jsPDF** | 纯前端生成 PDF，无需后端 |
| 路由模式 | **Hash 模式** | 静态托管无需服务端 rewrite，评委刷新任意子页面不会 404 |
| 演示链 | **Sepolia 测试网** | 公网可访问，评委可自行打开链接验证；合约源码已验证 |
| 规划：联盟链 | **FISCO BCOS** | 【规划中】对应大赛 PPT 的"联盟链环境配置"方向；适合"学校/期刊/组委会"多方共识场景 |

**选型的共同原则**：**优先选择有成熟生态、AI 可高比例辅助、且不需要额外学习成本的技术**，
以便在有限工期内把工程量集中在"存证与核验"这一核心功能上。

## 2.5 数据设计

### 2.5.1 链上数据结构

```solidity
enum WorkType { Paper, Code, Dataset, Other }   // 论文 / 代码 / 数据集 / 其他

struct Work {
    bytes32  contentHash;    // 当前版本文件 SHA-256 指纹
    address  author;         // 登记人钱包地址（即身份）
    uint64   registeredAt;   // 首次登记时间（链上时间戳）
    uint64   updatedAt;      // 最近一次变更时间
    uint8    aigcRatio;      // AIGC 介入比例 0-100
    WorkType workType;       // 成果类型
    string   title;          // 成果标题（短文本，直接上链）
    string   metaURI;        // 扩展元信息指针（预留 IPFS 等）
    bool     disputed;       // 是否处于争议中
    uint32   versionCount;   // 版本数（首次登记即为 1）
}
```

### 2.5.2 索引与存储布局

| 结构 | 类型 | 用途 |
| --- | --- | --- |
| `_works` | `mapping(uint256 => Work)` | 成果编号 → 成果数据 |
| `hashToWorkId` | `mapping(bytes32 => uint256)` | **指纹 → 成果编号，实现 O(1) 核验** |
| `versionHash` | `mapping(uint256 => mapping(uint32 => bytes32))` | 成果编号 → 版本号 → 指纹，**保留全部历史版本** |
| `_aigcTools` | `mapping(uint256 => string[])` | 成果编号 → AIGC 声明历史 |
| `workCount` | `uint256` | 成果总数（自增编号） |

**设计要点**：

- `hashToWorkId` 采用 mapping 直查，**核验成本不随存证总量增长**；
- `versionHash` 保留每个历史版本的指纹，因此**旧版本同样可以被单独核验**，这是"过程留痕"的技术基础；
- 核验函数 `verifyWork` 声明为 `view`，调用**不消耗 gas**，第三方核验零成本。

### 2.5.3 合约接口清单

| 接口 | 类型 | 权限 | 说明 |
| --- | --- | --- | --- |
| `registerWork(...)` | 写 | 任何人 | 登记新成果 |
| `addVersion(...)` | 写 | 仅成果作者 | 追加新版本 |
| `declareAIGC(...)` | 写 | 仅成果作者 | 声明 / 更新 AIGC 使用情况 |
| `raiseDispute(...)` | 写 | 任何人 | 发起争议 |
| `verifyWork(hash)` | **只读** | 任何人 | 核验指纹，返回成果信息（**0 gas**） |
| `getWork(id)` | 只读 | 任何人 | 查询成果详情 |
| `getVersionHash(id, ver)` | 只读 | 任何人 | 查询指定版本指纹 |
| `getAigcTools(id)` | 只读 | 任何人 | 查询 AIGC 声明历史 |
| `getWorkCountOf(addr)` | 只读 | 任何人 | 统计某地址的成果数 |

**事件**：`WorkRegistered` / `VersionAdded` / `AIGCDeclared` / `DisputeRaised` —— 完整事件便于链下索引。

### 2.5.4 权限与安全设计

| 风险 | 设计回应 |
| --- | --- |
| 越权修改他人成果 | `onlyWorkAuthor` 修饰器；非作者调用 `addVersion` / `declareAIGC` 直接 revert |
| 同一指纹重复登记 | `hashToWorkId` 唯一性校验，重复登记 revert |
| **挪用他人已登记指纹** | 追加版本前校验该指纹归属，若已属他人成果则拒绝（**确权冲突防护**） |
| 非法输入 | 零指纹、空标题、AIGC 比例 > 100、与当前版本相同指纹 —— 四类全部拒绝 |
| 管理员特权 | `admin` 声明为 `immutable`，**不存在"管理员改数据"的可能** |
| 重入攻击 | 合约**不涉及任何转账与外部调用**，不存在重入路径 |
| 整数溢出 | Solidity 0.8+ 内置检查 |
| 私钥管理 | 部署私钥仅存于本地 `.env`，已被 `.gitignore` 屏蔽；使用专用测试钱包 |

## 2.7 本章小结

本作品的设计可以用三句话概括：

1. **边界清晰** —— 只做"存证与核验"一层，不做查重算法、不做投稿系统、不做用户系统；
2. **信任最小化** —— 平台不持有原文、无管理员特权、记录一经写入不可修改，
   验证过程不依赖平台存续；
3. **成本可控** —— 只有 32 字节指纹与关键状态上链，核验为 0 gas 只读查询，
   完全规避了区块链在大数据量场景下的短板。

第 4 章将说明这些设计的**实际完成情况**，包括已通过测试与链上验证的部分，
以及尚存的局限与不足。
