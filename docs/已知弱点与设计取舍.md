## 弱点 1 ⭐ AIGC 工具名称未在登记时写入链上（**当前最主要的产品短板**）

### 现象

前端登记页允许用户勾选 AI 工具并填写用途，但在 2026-09-26 之前**这些文本从未上链**。

| 数据 | 是否上链 | 说明 |
| --- | --- | --- |
| 内容指纹（SHA-256） | ✅ 上链 | `Work.contentHash` |
| AIGC 介入**比例**（如 25%） | ✅ 上链 | `Work.aigcRatio` |
| 登记人、时间戳、标题、类型 | ✅ 上链 | `Work` 结构体 |
| **AI 工具名称与用途说明** | ❌ **未上链** | 仅存在于用户当次会话的界面中，刷新即丢失 |

### 根因（代码级核实）

- `registerWork(bytes32, string, WorkType, uint8, string)` 的参数表中**没有承载工具名的字段**；
  它只写入 `Work.aigcRatio`，第 5 个参数 `_metaURI` 的语义是「扩展元信息指针」。
- 工具名称只能通过**另一个函数** `declareAIGC(workId, ratio, tools)` 写入 `_aigcTools[workId]`。
- 前端登记流程**只调用了 `registerWork`**，从未调用 `declareAIGC`，因此 `getAigcTools()` 返回空数组。

### 证据

**链上实测**（Sepolia `0x0Caf124D677DF3250a6cc37772bcc9E0a1de125E` 的成果 #1）：

```
workCount = 1
成果 #1  标题   : "思想道德与法治"课社会实践报告书202503
         AIGC 比例: 25%          ← 已上链
         getAigcTools(1) = []    ← 空！工具名没上链
```

**自动化测试**：`blockchain/test/AcademicProof.test.js` 组6.5 用 3 个用例把该行为固定下来：

| 用例 | 断言 |
| --- | --- |
| `registerWork 之后 getAigcTools 为空数组（工具名丢失）` | `tools.length === 0` |
| `但比例确实已上链` | `aigcRatio === 25` |
| `必须显式调用 declareAIGC 才会留下工具名` | 调用后 `tools[0] === 'DeepSeek（用途：生成初步框架）'` |

> ⚠️ 修复该短板后，**这 3 个用例必须同步改为断言「已写入」**，否则测试会锁死错误行为。

### 当前采取的补救（2026-09-26 已完成）

1. **修正误导性文案**（必须做，否则等于界面造假）：
   登记成功页不再写「AIGC 声明（已上链）」，改为明确区分——
   比例标注「已上链」，工具名标注「**尚未上链**」并说明原因。
2. **提供补救入口**：成功页新增按钮「立即将声明写入链上」，点击后调用
   `declareAIGC`，用户再签一次名即可把工具名补写进链上。写入成功后显示绿色确认。
3. **登记页表单的默认成果类型修正**：原 `WORK_TYPE.Paper` 引用了模板作用域中未导入的标识符
   （运行时解析为 `undefined`，会覆盖成空字符串），已改为字面量 `0`。

### 影响评估（**写提案书时要如实说明**）

| 维度 | 影响 |
| --- | --- |
| 「文件原创性存证与核验」 | ✅ **无影响**。指纹核验是本项目的主干功能，完整可用 |
| 「AIGC 贡献存证」 | ⚠️ **有影响**。目前链上只能证明「作者声明 AI 占比 X%」，**无法证明用了哪些工具、做什么用** |
| 演示视频 | ⚠️ 需注意：0:25-0:55 那一镜若说「AIGC 声明已上链」，**必须同时说明比例已上链、工具名需补写一次**，或改用「立即写入」按钮后再讲 |
| 答辩追问 | 见下方预案 |

### 后续可选修复方案（**未实施，时间充裕时再做**）

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A. 改 `registerWork` 签名 | 增加 `string _aigcTools` 参数，登记时一次写入 `_aigcTools[workId]` | 需改合约、重新部署、**重新做 Etherscan 源码验证**、更新前端与测试；现有链上记录需重录、截图需重拍 |
| B. 前端登记流程自动补一次交易 | `registerWork` 确认后自动发 `declareAIGC` | 用户需签两次名；产生两笔交易；`workCount` 与事件时序略复杂 |
| C. 前端引导式（**当前采用**） | 保持合约不变，成功页提示并可一键补写 | 依赖用户主动点击；不能保证「登记即完整」 |

**决策记录**：2026-09-26 经与作者确认，**选择 C 并如实归档本弱点**，暂不改合约。
理由：当前主干功能（存证 + 核验）已完整可用且证据齐全，改合约会使既有测试证据链失效，性价比不高。
**若最终不修改，本项将作为「项目不足与改进方向」写入提案书。**

### 答辩预案（评委若追问）

> **问**：你说能存证 AIGC 贡献，那 AI 到底写了哪部分，链上有吗？
>
> **答（如实）**：链上记录的是作者声明的 **AIGC 介入比例**与时间戳，这部分是不可篡改的。
> 但**具体的 AI 工具名称与用途说明目前尚未在登记时写入链上**——这是我们发现并已在界面明确标注的不足，
> 目前通过「登记后补写声明」的方式弥补。完整方案是扩展登记接口，让工具名与比例在同一次交易内上链，
> 这需要重新部署合约，我们评估后将其列为下一步改进项，而不是在文档里含糊过去。

## 弱点 2 时间轴的时间精度不足（已知，有意取舍）

### 现象

存证详情页的时间轴中，**历史版本与 AIGC 声明的具体时间用「最近更新时间」近似显示**，
并非每次操作的真实时间。

### 根因

合约的 `Work` 结构体只保存 `registeredAt`（首次登记）与 `updatedAt`（最近更新）两个时间戳。
每次 `addVersion` / `declareAIGC` 的真实时间**只存在于链上事件日志**中，没有落到可查询的状态里。

### 证据与现状

- 页面时间轴下方已主动注明：「合约只保存『最近更新时间』，历史版本与 AIGC 声明的具体时间由链上事件日志承载。
  演示阶段以最近更新时间为近似」。
- `docs/演示脚本-逐秒版.md` 2:20 那一镜的时间轴仍可正常展示，只是时间戳为近似值。

### 后续修复方案

前端改用 `contract.queryFilter(contract.filters.VersionAdded(...))` 读取事件日志，
即可拿到每一次操作的真实区块时间。**工作量约 1-2 小时，不涉及合约改动与重新部署。**

## 弱点 3 数据看板为全量遍历读取（演示规模可用，不具备扩展性）

### 现象

`DashboardView.vue` 通过 `for (let i = 1; i <= workCount; i++)` 逐条调用 `getWork(i)` 读取全部成果，
再在前端做统计。

### 影响与边界

- 当前链上仅 1 条记录，**性能完全无问题**。
- 若存证量增长到数千条，前端会发出数千次 RPC 请求，体验显著劣化。

### 后续修复方案

改为读取链上事件（`getWorkRegistered` 等）建立本地索引，或引入 The Graph 之类的索引服务。
**属生产化改造，超出本次 demo 范围**——在提案书中作为「工程扩展方向」说明即可。

## 弱点 4 数据看板未使用 ECharts 图表

### 现象

架构设计文档中曾计划用 ECharts 绘制饼图/柱状图，当前实现用 **CSS 进度条**呈现 AIGC 比例分布与类型分布。

### 原因与评估

引入 ECharts 会增加约 200KB+ 打包体积；当前 CSS 分布图在视觉上已能清晰表达分布，
且答辩展示效果无实质差异。**属有意的工程取舍，不是能力缺失。**

### 是否修复

看阶段5 之后的时间余量。若要修复，成本约 1 小时（`npm i echarts` + 替换两个分布块）。
