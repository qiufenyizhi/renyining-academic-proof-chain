### 3.2.2 数据结构：`Work` 结构体逐字段说明

```solidity
struct Work {
    bytes32 contentHash;   // 当前版本文件 SHA-256 指纹
    address author;        // 登记人钱包地址（身份即地址）
    uint64  registeredAt;  // 首次登记时间（链上时间戳）
    uint64  updatedAt;     // 最近一次变更时间
    uint8   aigcRatio;     // AIGC 介入比例 0-100
    WorkType workType;     // 成果类型
    string  title;         // 标题（短文本，直接上链）
    string  metaURI;       // 扩展元信息指针（留作 IPFS 等）
    bool    disputed;      // 是否处于争议中
    uint32  versionCount;  // 版本数，首次登记即为 1
}
```

| 字段 | 类型 | 写入时机 | 登记后可否变更 | 设计理由 |
| --- | --- | --- | --- | --- |
| `contentHash` | `bytes32` | `registerWork` | ✅ 仅通过 `addVersion` | 核验的唯一依据；**只有指纹上链，原文不上链** |
| `author` | `address` | `registerWork` | ❌ **永不可变** | 身份即地址，避免出现"过户"这种需要信任的操作 |
| `registeredAt` | `uint64` | `registerWork` | ❌ **永不可变** | 先权利证明的时间锚点，改了整条记录就失去意义 |
| `updatedAt` | `uint64` | 登记 / 追加版本 / 声明 AIGC | ✅ | 供时间轴展示"最近活动" |
| `aigcRatio` | `uint8` | `registerWork` / `addVersion` / `declareAIGC` | ✅ 可更新 | 允许作者细化申报；**每次变更都留事件** |
| `workType` | `enum`(uint8) | `registerWork` | ❌ 不提供修改入口 | 类型是分类检索维度，改动收益低于复杂度 |
| `title` | `string` | `registerWork` | ❌ 不提供修改入口 | 标题一旦上链即固定，避免"标题漂移"使核验叙事含糊 |
| `metaURI` | `string` | `registerWork` | ❌ 不提供修改入口 | 预留扩展位，demo 阶段通常为空串 |
| `disputed` | `bool` | `raiseDispute` | ⚠️ **只能由 false 变 true** | 争议标记只增不减（见 3.2.11） |
| `versionCount` | `uint32` | `registerWork`（置 1）/ `addVersion` | ✅ 只增 | 首次登记即第 1 版，语义上"登记本身就是一个版本" |

**时间戳为什么用 `uint64` 而不是 `uint256`？** 两个字段各用 `uint64` 可与 `author`（20 字节）
及 `uint8`、`bool` 打包进更少的 32 字节槽位，降低存储与 gas 开销；`uint64` 秒级时间戳在
天文尺度上也不会溢出。

### 3.2.3 存储布局与"O(1) 核验"的实现原理

| 状态变量 | 类型 | 可见性 | 用途 |
| --- | --- | --- | --- |
| `admin` | `address immutable` | `public` | 部署者地址；编译器将其写入字节码而非存储槽，读取不花 gas |
| `workCount` | `uint256` | `public` | 已登记的成果总数，同时是 workId 分配计数器 |
| `_works` | `mapping(uint256 => Work)` | **private** | 成果全量数据；外部只能通过 `getWork` 读取 |
| `hashToWorkId` | `mapping(bytes32 => uint256)` | `public` | **指纹 → 成果 ID**，核验的核心索引 |
| `versionHash` | `mapping(uint256 => mapping(uint32 => bytes32))` | `public` | 每个成果的**全部历史版本指纹** |
| `_aigcTools` | `mapping(uint256 => string[])` | **private** | AIGC 工具声明的追加式历史；通过 `getAigcTools` 读取 |

**O(1) 核验的实现**：`verifyWork` 只做一次 `hashToWorkId[_contentHash]` 映射查找，
命中即返回记录，未命中即返回 `exists = false`。**查找代价与链上记录总数无关**——
这正是"验证成本趋近于零、任何第三方都能自行复现"的技术基础。

> 与之对照：`getWorkCountOf` 需要遍历全部成果，是 **O(n)** 的辅助统计函数，
> 且为 `view`（不耗 gas）。它只用于"我的存证"这类展示，**不参与核验路径**。

### 3.2.4 为什么 workId 从 1 开始

`hashToWorkId` 的默认值是 `0`，合约用 `0` 表示"**该指纹从未被登记**"。
若 `workId` 从 `0` 开始，就无法区分"第 0 号成果"与"未登记"。因此：

- `registerWork` 用 `workId = ++workCount`，首个成果 workId = **1**；
- `verifyWork` 中 `if (workId == 0) return (false, ...)`；
- `addVersion` 中若 `hashToWorkId[新指纹]` 既非 0 也不等于本成果 ID，则拒绝（防挪用）。

这三处共用同一个哨兵约定，是合约内部最重要的隐式契约。

### 3.2.5 修饰器

| 修饰器 | 检查 | 失败错误 | 用于 |
| --- | --- | --- | --- |
| `onlyExisting(workId)` | `_works[workId].author != address(0)` | `NotFound()` | `addVersion`、`declareAIGC`、`raiseDispute` |
| `onlyWorkAuthor(workId)` | `_works[workId].author == msg.sender` | `NotAuthor()` | `addVersion`、`declareAIGC` |

> **注意一个刻意的例外**：`raiseDispute` 只要求成果存在，**不要求调用者是作者**——
> 争议本来就应由第三方发起。这是权限设计里唯一一处"故意放开"的地方。

### 3.2.6 逐函数详细说明

#### ① `registerWork` —— 登记新成果（主干功能）

```solidity
function registerWork(
    bytes32 _contentHash,
    string calldata _title,
    WorkType _type,
    uint8 _aigcRatio,
    string calldata _metaURI
) external returns (uint256 workId)
```

| 项 | 内容 |
| --- | --- |
| 访问控制 | 无（任何地址均可登记；`msg.sender` 即成为作者） |
| 前置校验 | ① `_contentHash != 0`，否则 `ZeroHash()`<br>② `hashToWorkId[_contentHash] == 0`，否则 `AlreadyRegistered()`<br>③ `_aigcRatio <= 100`，否则 `InvalidRatio()`<br>④ `bytes(_title).length > 0`，否则 `EmptyTitle()` |
| 状态变更 | `workCount++` → 写入 `_works[workId]`（`versionCount = 1`）→ `hashToWorkId[指纹] = workId` → `versionHash[workId][1] = 指纹` |
| 事件 | `WorkRegistered(workId, contentHash, author, timestamp, title)`，前三个字段带 `indexed` |
| 返回 | `workId`（从 1 开始） |
| 实测 gas | **平均 244,400**（含 title 与 metaURI 两个字符串的存储） |
| 失败情形 | 指纹为全零 / 同一文件被登记过 / 比例越界 / 标题为空 |

**设计要点**：`if (hashToWorkId[_contentHash] != 0) revert AlreadyRegistered();`
使"**同一份文件不能登记两次**"。这条规则的价值是：一个指纹在全网唯一对应一条记录，
因此核验结果不产生歧义——**不需要问"是哪一次登记的"，因为只可能有一次**。

#### ② `addVersion` —— 追加新版本（过程留痕）

```solidity
function addVersion(uint256 _workId, bytes32 _contentHash, uint8 _aigcRatio)
    external onlyExisting(_workId) onlyWorkAuthor(_workId)
```

| 项 | 内容 |
| --- | --- |
| 访问控制 | **仅成果作者**（`NotAuthor()`） |
| 前置校验 | ① 成果存在；② 必须是作者；③ 新指纹非全零；④ 比例 ≤ 100；⑤ 新指纹 ≠ 当前指纹（`SameHash()`）；⑥ 新指纹未被**其他**成果占用（`AlreadyRegistered()`） |
| 状态变更 | `versionCount++`；`contentHash` 更新为新指纹；`aigcRatio` 更新；`updatedAt` 刷新；`versionHash[workId][新版本号] = 新指纹`；`hashToWorkId[新指纹] = workId` |
| 事件 | `VersionAdded(workId, version, contentHash, aigcRatio)` |
| 实测 gas | **86,681** |

**关键设计（也是本项目"过程留痕"的技术含义）**：
追加版本时**不会删除旧指纹的映射**。因此第 1 版的指纹与第 2 版的指纹**都能通过核验**，
且 `getWork` 返回的 `contentHash` 指向当前版本。前端据此判断"这份文件是当前版本还是历史版本"
（`isCurrentVersion = work.contentHash === 上传指纹`），从而把"曾经存在"与"现在有效"区分开。

#### ③ `declareAIGC` —— 声明 AI 使用情况（核心差异化功能）

```solidity
function declareAIGC(uint256 _workId, uint8 _ratio, string calldata _tools)
    external onlyExisting(_workId) onlyWorkAuthor(_workId)
```

| 项 | 内容 |
| --- | --- |
| 访问控制 | 仅成果作者 |
| 前置校验 | 成果存在；是作者；`_ratio <= 100` |
| 状态变更 | 更新 `aigcRatio` 与 `updatedAt`；将 `_tools` **追加**到 `_aigcTools[workId]` |
| 事件 | `AIGCDeclared(workId, ratio, tools)` |
| 实测 gas | **95,567** |

**为什么要单独设一个函数，而不是在登记时一次写完？**
因为"**比例**"与"**具体工具与用途**"这两类信息的稳定程度不同：比例可以先用一个估计值登记，
工具与用途可能随后细化。分开后，作者可以在不重新登记、不改变时间戳的前提下补全申报，
而每一次申报都留下独立事件，形成**可追溯的申报历史**（`getAigcTools` 返回数组而非单值）。

> ⚠️ **必须如实说明的实现现状**：`registerWork` 只把 `aigcRatio` 写入 `Work`，
> **工具名不在这一次交易中上链**，需再调用一次 `declareAIGC` 才能进入 `_aigcTools`。
> 这一行为已被测试组 6.5 固定下来（`blockchain/test/AcademicProof.test.js`），
> 界面也已如实标注并提供"立即将声明写入链上"入口。
> 详细说明与改进方案见 `docs/已知弱点与设计取舍.md` 弱点一及本章 3.2.11。

#### ④ `verifyWork` —— 核验（演示核心，也是产品定位的落点）

```solidity
function verifyWork(bytes32 _contentHash) external view
    returns (bool exists, uint256 workId, address author, uint64 registeredAt, uint8 aigcRatio, string memory title)
```

| 项 | 内容 |
| --- | --- |
| 访问控制 | **无**——任何人、任何地址、不需要授权 |
| 状态变更 | **无**（`view` 函数，不产生交易） |
| 实测 gas | **0**（`eth_call` 链下执行，不上链、不花手续费） |
| 命中 | `(true, workId, author, registeredAt, aigcRatio, title)` |
| 未命中 | `(false, 0, address(0), 0, 0, "")`——**返回 false 而不是 revert** |

**为什么"未登记"用返回值而不是报错？** 因为"这份文件没有存证记录"是一个**正常的、预期的结论**，
不是异常。用返回值表达使调用方（前端、其他合约、脚本）可以用同一段代码处理两种结果，
也避免了在核验页触发一次无意义的异常提示。

**谁可以核验？** 这是本作品与"平台自证"式产品的分界线：核验方可以是期刊编辑、
竞赛组委会、教务老师，**甚至是一个完全不知道本作品存在的第三方**——
只要能访问公开 RPC 与这份合约地址，他就能自己算出结论（复现命令见 4.5.3）。

#### ⑤ `raiseDispute` —— 登记争议

```solidity
function raiseDispute(uint256 _workId, string calldata _reason) external onlyExisting(_workId)
```

| 项 | 内容 |
| --- | --- |
| 访问控制 | **任意地址**（不限于作者） |
| 状态变更 | `disputed = true` |
| 事件 | `DisputeRaised(workId, raiser, reason)`——`workId` 与 `raiser` 带 `indexed` |
| 实测 gas | **32,865** |

**这个函数的定位必须说清楚**：它做的是**争议登记**（把"有人提出异议 + 理由 + 提出人 + 时间"
留成不可篡改的记录），**不是争议裁决**。合约中没有仲裁、没有撤销、没有质押。
之所以这样设计，是因为裁决需要引入"谁是裁判"这一新的信任假设，
而在 demo 阶段引入一个中心化裁判会**反过来削弱**整条链路的独立性。
诚实地说，这是一个功能上的缺口而不是优点，已在 3.2.11 与 4.2 节列为局限。

### 3.2.7 事件定义与链下索引

| 事件 | 参数（`indexed` 已标注） | 触发点 | 链下用途 |
| --- | --- | --- | --- |
| `WorkRegistered` | `workId`(I)、`contentHash`(I)、`author`(I)、`timestamp`、`title` | `registerWork` | 按作者 / 按指纹 / 按 ID 检索；**前端从中解析 workId** |
| `VersionAdded` | `workId`(I)、`version`、`contentHash`、`aigcRatio` | `addVersion` | 重建版本历史 |
| `AIGCDeclared` | `workId`(I)、`ratio`、`tools` | `declareAIGC` | 重建 AI 申报历史 |
| `DisputeRaised` | `workId`(I)、`raiser`(I)、`reason` | `raiseDispute` | 争议列表与提出人追溯 |

**为什么事件参数要带 `indexed`？** 带 `indexed` 的字段进入 topics，可被节点按值过滤
（例如"某作者的全部存证"）。这是"链上只存最小状态、完整履历由事件承载"这一分层思路的落地：
**状态变量回答"现在是什么"，事件回答"发生过什么"。**

前端目前使用事件的地方是 `RegisterView.submit()`：交易回执返回后，
逐个解析 `receipt.logs` 并匹配 `WorkRegistered` 来取得 `workId`——
比"再查一次 `workCount`"更可靠（并发登记时不会取错）。

### 3.2.8 自定义错误定义表

| 错误 | 触发条件 | 前端中文提示（`abi.js` 的 `ERROR_MESSAGE`） |
| --- | --- | --- |
| `ZeroHash()` | 指纹为全零 | 文件指纹无效（全零），无法存证。 |
| `AlreadyRegistered()` | 指纹已被登记（登记）或被其他成果占用（追加版本） | 该文件指纹已被登记过。同一份文件不能重复存证；若内容有更新，请使用「版本追加」。 |
| `InvalidRatio()` | `aigcRatio > 100` | AIGC 介入比例必须在 0 - 100 之间。 |
| `EmptyTitle()` | 标题为空串 | 成果标题不能为空。 |
| `NotFound()` | 对不存在的 workId 调用需存在性校验的函数 | 未找到该成果，请确认成果编号是否正确。 |
| `NotAuthor()` | 非作者调用 `addVersion` / `declareAIGC` | 只有该成果的登记人才能执行此操作。 |
| `SameHash()` | 追加的新指纹与当前版本相同 | 新版本指纹与当前版本完全相同，无需追加。 |

**为什么用自定义错误而不是 `require` 字符串？** 自定义错误只编码 4 字节选择器（必要时附带参数），
不需存储字符串，**更省 gas**；同时它是类型化的，前端可以把选择器映射为中文提示——
这正是 `abi.js` 中把 7 个 `error` 片段显式写进 ABI 的原因。
（真实网络的踩坑记录：RPC 只回 `execution reverted`，错误名需从 `e.data` 的选择器反推，
详见 `docs/环境搭建手册.md` 与 5.4.6 节。）

### 3.2.9 成果生命周期（状态机）

```
                 registerWork                       addVersion（仅作者）
   [不存在] ──────────────────────> [已登记 v1] ──────────────────────> [已登记 vN]
       │                                 │  ▲                                  │
       │                                 │  └──── declareAIGC（仅作者，可多次）┘
       │                                 │
       │                                 └──── raiseDispute（任意地址）──> [已登记 + disputed = true]
       │                                                                        （不可撤销）
       └── verifyWork(任意指纹) ──> exists = false（未登记）
```

要点：
1. **只有"新增"与"追加"，没有任何删除或修改历史的能力**——合约未提供 `delete`、`updateTitle`、
   `transferAuthor` 等接口；
2. `disputed` 是**单向开关**；
3. `verifyWork` 是唯一不改变状态的入口，且对所有人开放。

### 3.2.10 关键设计决策与代价（如实列出取舍）

| 决策 | 收益 | 代价（已接受的） |
| --- | --- | --- |
| **合约不可升级、无 owner 管理接口** | 已写入的记录**连作者和部署者都改不了**，核验结论不依赖对任何人的信任 | 发现设计缺陷只能重新部署，旧地址的历史记录留在旧合约 |
| **`admin` 只记录、不参与任何权限判定** | 不存在"管理员作恶"的攻击面 | `admin` 实际是**未使用的字段**，仅作部署溯源用（3.2.11 说明） |
| **只有指纹与短文本上链，原文不上链** | 隐私、成本、可扩展性同时成立 | 无法从链上还原内容，只能验证"是否一致" |
| **`view` 核验 + O(1) 映射** | 核验零成本、零等待、可无限次复现 | 需要核验方自行取得公开 RPC（Sepolia 为完全公开） |
| **custom errors** | 省 gas、类型化、可映射中文 | 旧版工具链对错误名的解析支持不一致（本项目已用选择器方案绕过） |
| **计数器用 `unchecked`** | 省去不可能发生的溢出检查开销 | 需在注释中说明"不可能溢出"的前提（代码已注明） |
| **同一指纹全局唯一** | 核验结果无歧义 | 内容有更新必须走"版本追加"，用户需理解这一概念（界面已用文案引导） |

### 3.2.11 边界行为与已知局限（**主动列出，避免夸大**）

| # | 行为 | 说明 | 是否影响主干 |
| --- | --- | --- | --- |
| 1 | `getWork` 对不存在的 ID 返回全零结构 | 该函数**未加** `onlyExisting`。前端以 `author == 0x000...0` 判断"不存在" | ❌ 不影响（前端已处理） |
| 2 | `addVersion` 允许把**本成果的历史版本指纹**再次追加 | 只校验"不等于当前版本指纹"，因此可能产生一条冗余版本记录（不影响任何指纹的归属与核验结论，仅使版本号多一条） | ❌ 不影响正确性，属冗余 |
| 3 | `disputed` 只能置 `true`，无撤销 | 合约不含仲裁与撤销流程，争议仅作为标记存在 | ⚠️ 功能缺口（已在 4.2 节列为局限） |
| 4 | `admin` 不参与任何权限校验 | 合约中除构造函数外**没有一处读取 `admin`**；它是部署者溯源字段，不是管理员权限 | ❌ 不影响（但文档中不应称其为"管理员"） |
| 5 | `registerWork` 不写入 AIGC 工具名 | 工具名须由 `declareAIGC` 单独写入；测试组 6.5 固定了该行为 | ⚠️ 削弱"AIGC 贡献存证"叙事（弱点一） |
| 6 | `workType`、`title`、`metaURI` 登记后不可修改 | 无修改入口；如需变更只能新登记（但同一指纹不能重复登记，故实际是"内容变了才能再登记"） | ❌ 不影响，属设计取舍 |
| 7 | 时间戳取 `block.timestamp` | 由出块者决定，非权威授时（TSA）；偏差量级为秒 | ❌ 演示级足够，已在第 2 章说明 |

> 上表第 3、5 项是**真正影响产品完整性的两项**，本章与第 4 章、第 6 章均按同一口径陈述，
> 不因"写在详细设计里"而淡化。

### 3.3.3 状态管理：模块级单例 composable（为什么不用 Pinia）

`useWallet.js` 把状态声明在**模块顶层**（`provider`、`signer`、`contract`、`readContract`、
`address`、`chainId`、`balance`、`connecting`），导出的 `useWallet()` 每次调用**返回同一批 ref**。

```
模块顶层（单例，模块只求值一次）
├── provider      BrowserProvider | null    只读查询用
├── signer        Signer | null             写交易用
├── contract      Contract | null           可写合约实例
├── readContract  Contract | null           只读合约实例（JsonRpcProvider，无需钱包）
├── address       ref('')                   当前账户地址
├── chainId       ref(0)                    当前链 ID
├── balance       ref('0')
└── connecting    ref(false)
        │
        └── useWallet() → { 状态 ref, computed, connect, disconnect, switchChain,
                            refreshBalance, requireContract, ensureReadContract }
```

| 设计点 | 实现 | 理由 |
| --- | --- | --- |
| 全局共享 | 模块作用域变量 + `useWallet()` 返回引用 | 5 个页面都需要钱包状态，**Pinia 对 8 个 ref 的状态量属过度设计**，且少一个依赖 |
| 双合约实例 | 可写 `contract`（Signer）+ 只读 `readContract`（`JsonRpcProvider`） | **核验页必须做到"不连钱包也能用"**——这是产品定位，不是可选项 |
| 只读实例懒加载 | `ensureReadContract()` 首次调用时创建 | 只要用户不打开核验/登记页，就不建立 RPC 连接 |
| 事件绑定只做一次 | 模块级 `bound` 标志 | 多个组件调用 `useWallet()` 时不会重复注册监听器 |
| `accountsChanged` | 空数组 → `disconnect()`；否则重新 `connect()` | 重连才能拿到新 signer |
| `chainChanged` | **整页 `location.reload()`** | 网络切换后旧 provider/contract 实例可能失效，重载最稳妥 |
| 链切换 | `wallet_switchEthereumChain`，错误码 `4902` 时回退 `wallet_addEthereumChain` | 兼容钱包中尚未添加该网络的情况 |
| 错误前置 | `requireContract()` 在未连接时抛出中文提示 | 避免写操作在缺少 signer 时产生晦涩报错 |

#### `FileDropzone.vue`（承载"文件不上传"这一核心卖点）

| 项 | 内容 |
| --- | --- |
| 职责 | 拖拽/点击选择文件 → **浏览器本地**计算 SHA-256 → 展示文件名、大小、完整指纹、本地耗时 |
| props | `title: String`（默认"拖拽文件到此处，或点击选择"）、`subTitle: String`、`showCost: Boolean`（默认 `true`） |

### 3.3.5 工具层详细设计

#### `utils/hash.js`（项目技术亮点所在）

| 导出 | 签名 | 说明 |
| --- | --- | --- |
| `sha256File` | `async (file: File) => Promise<string>` | `file.arrayBuffer()` → `crypto.subtle.digest('SHA-256', buf)` → 32 字节转 `0x` + 小写十六进制 |
| `sha256Text` | `async (text: string) => Promise<string>` | 文本哈希，用于演示与测试 |
| `sha256FileTimed` | `async (file: File) => Promise<{hash, costMs}>` | 用 `performance.now()` 计时，`costMs` 保留 1 位小数（演示 D1 显示耗时） |
| `formatBytes` | `(bytes: number) => string` | 人类可读大小（B/KB/MB/GB） |
| `shortHash` | `(hash, head = 10, tail = 6) => string` | 指纹缩略显示 `0x7f3a9c...a1b2` |

**输出格式的约定**：`0x` + 64 位小写十六进制，**与 Solidity 的 `bytes32` 和 `ethers.sha256()`
结果完全一致**。这一点很关键：如果前端输出的编码与合约期望的不一致，
核验会永远失败——所以该格式在 `verify-abi-match.mjs` 与测试中都被固定。

#### `utils/format.js`

| 导出 | 签名 | 用途 |
| --- | --- | --- |
| `shortAddress` | `(addr, head = 6, tail = 4) => string` | 地址缩略 `0x1a2b...3c4d` |
| `formatTimestamp` | `(ts: number\|bigint) => string` | 链上秒级时间戳 → `YYYY-MM-DD HH:mm:ss` 本地时间 |
| `relativeTime` | `(ts) => string` | 时间轴用相对时间（刚刚 / N 分钟前 / N 天前） |
| `aigcLevel` | `(ratio) => {type, text}` | 比例语义化：0 完全人工 / ≤30 轻度辅助 / ≤60 中度参与 / >60 高度依赖 |

#### `utils/certificate.js`

| 导出 | 签名 | 说明 |
| --- | --- | --- |
| `exportCertificate` | `(data) => boolean` | 依据数据生成证书 HTML → 打开新窗口 → 调用 `window.print()` |
| `buildCertificateHtml` | `(data) => string` | 证书 HTML 模板（含防 XSS 的 `esc()` 转义） |
| `buildDocTitle` | `(workId, title) => string` | 生成 PDF 建议文件名 |

**为什么证书走"浏览器打印"而不是 jsPDF？**（这是本项目一次真实的返工，详见 5.4.6 节）
jsPDF 默认使用 PDF 标准字体（Helvetica / WinAnsi 编码），**不含中文字形**，
导出的证书中文全部乱码。改为"HTML 模板 + 浏览器打印为 PDF"后，
浏览器会嵌入中文字体子集（验证结果：PDF 内含 `FontFile2`、`ToUnicode`、
`Subtype/Type0`、`Identity-H`，字体为 MicrosoftYaHei 子集，文件 144.9 KB），
中文正常显示；同时前端**移除了 jsPDF 依赖**，详情页 chunk 从 374.24 KB 降到 18.63 KB。

**文件名规则**（`buildDocTitle`）：`存证证书_#{workId}_{标题}`，其中标题做四步净化——
① 非法字符 `\ / : * ? " < > |` 替换为 `_`；② 连续空白折叠为单个空格；
③ 超过 `MAX_TITLE_LEN = 40` 字符则截断；④ 标题为空则省略该段。
共 8 个用例固定在 `frontend/scripts/test-cert-filename.mjs`。

#### `contracts/abi.js`

| 导出 | 说明 |
| --- | --- |
| `CONTRACT_ABI` | **人类可读 ABI 数组**：8 个只读 + 1 个核验 + 4 个写入 + 4 个事件 + **7 个自定义错误** |
| `WORK_TYPE` | 枚举数值映射（Paper 0 / Code 1 / Dataset 2 / Other 3），与合约 `enum` 一一对应 |
| `WORK_TYPE_LABEL` / `WORK_TYPE_TAG` | 类型的中文名与标签配色 |
| `ERROR_MESSAGE` | 自定义错误 → 中文提示的映射表（7 条，见 3.2.8） |
| `parseContractError(err)` | 异常 → 用户可读中文：① 用户取消交易；② 余额不足；③ 网络异常；④ 从消息中解析 `custom error 'X('` 并查表；⑤ 兜底输出原始信息（**不静默吞掉**） |

> **如实说明该函数的能力边界**：真实网络只回 `execution reverted`，
> 自定义错误名仅存在于返回数据的 4 字节选择器中。ABI 中显式声明 7 个 `error` 片段后，
> ethers v6 可将其解码为带名称的异常，`parseContractError` 才能命中第 ④ 步；
> 若某节点返回的数据无法解析，则退化为第 ⑤ 步的兜底文案（会附上原始信息便于排查）。

> **`declareAigcNow()` 的存在本身就是诚实性的体现**：界面不会在 `registerWork` 成功后
> 谎称"AI 工具已上链"，而是明确告诉作者工具名还需一次交易——这正是弱点一在前端的如实落地。

#### ③ `VerifyView.vue` —— 成果核验（核验方视角）⭐

### 3.3.7 两条核心时序

**时序一：存证登记（作者）**

```
浏览器                    链（Sepolia）                 用户
  │                          │                            │
  │  <── 选择文件 ──────────────────────────────────────────┘
  │  file.arrayBuffer()      │                            │
  │  crypto.subtle.digest    │   （无任何网络请求）        │
  │  ──> hash + costMs       │                            │
  │                          │                            │
  │  verifyWork(hash) ───────┼──> view 查询（预检查）      │
  │  <── exists = false ─────┼──                          │
  │                          │                            │
  │  registerWork(hash,…) ───┼──> 交易（MetaMask 签名）    │
  │  <── receipt ────────────┼── WorkRegistered 事件       │
  │  解析事件取 workId       │                            │
  │  getWork(workId) ────────┼──> 补全 registeredAt        │
  │  <── 展示 workId/时间/gas/声明 ──────────────────────────┘
  │  （可选）declareAIGC ────┼──> 把工具名写入链上
```

**时序二：成果核验（第三方，无需钱包）**

```
浏览器                                 链（公开 RPC）
  │                                       │
  │  <── 拖入待核验文件                    │
  │  本地算 SHA-256（文件不离开设备）       │
  │  verifyWork(hash) ────────────────────┼──> O(1) 映射查找
  │  <── exists / workId / author / 时间 ──┼──
  │  命中：getWork(workId) ───────────────┼──> 类型/版本/争议状态
  │  <── 大字「核验通过」+ 链上元信息 + Etherscan 链接
  │  未命中：大字「核验失败」+ 失败原因说明
```

**这两条时序的对称性就是产品的核心论证**：右侧（链）对所有参与方是同一份公开数据，
左侧（浏览器）各自独立计算；**中间不存在"本平台的服务器"这个角色**。

## 3.7 本章小结

详细设计要回答的其实只有一个问题：**"这份作品声称的能力，是否真的落在代码里。"**

本章据此给出了三类可验证的答案：

1. **合约层面**：10 个对外接口逐一定义了访问控制、校验、状态变更、事件与 gas，
   并主动列出 7 项链上边界行为与 7 项设计取舍的代价；
2. **前端层面**：文件不上传不是承诺而是"代码中不存在上传路径"，
   核验不需要钱包不是便利而是产品定位的技术落地；
3. **接口层面**：ABI、组件契约、模块签名、配置来源全部明确，
   使第三方可以按 4.5.3 的命令自行复现核心结论。

**下一步**：第 4 章将说明这些设计的**实际完成情况**——
哪些已通过测试与链上验证（含 Sepolia 已部署合约与 Etherscan 源码验证）、
哪些是部分实现、哪些仍为规划中。
